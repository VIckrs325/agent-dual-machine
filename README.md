# 双机混合 Agent 工程

> 一台没有独显的轻薄本做控制端，一台 RTX 2060 笔记本做算力端，
> 用本地 4B 模型跑一个真正驻在 QQ 群里、会搜索、会算数、会记事的机器人。
>
> 这个仓库记录的不是"我跑通了某个 demo"，而是**把它跑稳**的过程：
> 每一次误判、每一个 4.3 秒的重载、每一条被模型编出来的数字，都在 `docs/` 里留了案。

---

## 为什么是两台机器

轻薄本只有 16GB 内存、没有独显，跑不了本地模型；2060 那台有 6GB 显存但常年放在桌上。
所以拆成两边：

- **控制端**（Windows）：写代码、改配置、看日志、推送密钥
- **算力端**（Ubuntu）：只跑 Ollama + 服务，不做开发

两边的边界很清楚：**需要碰硬件的放右边，需要人盯着改的放左边**。

```
        ┌───────────────────────┐            ┌──────────────────────────┐
        │  控制端  Windows      │            │  算力端  Ubuntu 24.04    │
        │  i5-12450H / 16GB     │   SSH      │  i7-9750H / 32GB         │
        │  无独显                │ ────────▶  │  RTX 2060 6GB            │
        │                       │            │                          │
        │  · 改代码 / 改配置     │            │  ┌────────────────────┐  │
        │  · scripts/secrets.mjs│  推送密钥   │  │ Ollama  qwen3.5:4b │  │
        │  · 看 journalctl      │ ────────▶  │  │ 127.0.0.1:11434    │  │
        └───────────────────────┘  (tmpfs)   │  └─────────▲──────────┘  │
                                             │            │             │
                                             │  ┌─────────┴──────────┐  │
                                             │  │ qq-bridge.mjs      │  │
                                             │  │ 规则0ms + 模型~1.1s│  │
                                             │  └─────────▲──────────┘  │
                                             │            │ WS 3001     │
                                             │  ┌─────────┴──────────┐  │
                                             │  │ SnowLuma (OneBot)  │  │
                                             │  └─────────▲──────────┘  │
                                             └────────────┼─────────────┘
                                                          │
                                                       QQ 群
```

## 三个档位

同一个 4B 模型，按"要不要碰这台机器"切成三档：

| 档 | 是什么 | 耗时 | 能做什么 |
|---|---|---|---|
| **A** | QQ 群里的机器人（`bridge/`） | 规则 0ms / 模型 1.1s | 聊天、搜索、算数、记人、偶尔主动插话 |
| **B** | 搜索 + 总结（`btask/`） | 9～350s（四档 profile） | 多轮检索、交叉核对、补充搜索后成文，**不碰文件系统** |
| **C** | 会动手的任务（`ctask/`） | ~185s/任务 | 读文件、写文件、跑命令、多步串行 |

判定标准就一句话：**B 档碰不到本机，需要碰本机就走 C 档。**
C 档的数字类任务必须过一层 `scripts/task-verify.mjs` 用代码复核 —— 因为 4B 心算大数是必错的，这一点下面有例子。

## 四个值得看的设计

### 1. 搜索判定：规则快通道 + 模型单 token + 置信度三档

最初用纯正则判断"这句话要不要联网"，结果在**中文指代词**上翻车：

```
「刚刚说的几个数字排个序」  → 被判成需要联网 → 反问「要我帮你搜一下吗」
「我刚才说的第一句话是什么」→ 同上
```

`刚刚 / 上面 / 现在` 在中文里首先是指代词，不是时效词。加正则只会越来越长、越来越脆。改成让模型做一次单 token 判定：

```
① 规则快通道（0ms）   显式「搜一下」/ 太短 / 代码类 → 直接决策，不花时间
② 模型判定（~167ms）   num_predict:1、temperature:0、think:false、logprobs
③ 置信度分档           pS>0.85 搜 | pS<0.45 不搜 | 灰区退回规则
④ 超时 600ms          退回规则结论，不硬判"不搜"
```

实测 18 条难样本 **16 条正确、平均 167ms**，而且能分清语义几乎相同的两句：

| 输入 | 判定 | 置信度 |
|---|---|---|
| 刚才那个股票现在多少 | 搜 | 0.995 |
| 我刚才说的第一句话是什么 | 不搜 | 0.001 |

**判定请求必须和主请求用同一个 `num_ctx`**，否则每轮白扔 4.3 秒（见下面"踩过的坑"）。

### 2. 算数不走模型：`<calc>` 标签 + 白名单求值

4B 会给出正确的 Python 代码，然后自己算错结果：

```
问：6185466 减 615563
答：print(6185466 - 615563)       ← 代码对
再问：告诉我结果
答：29903                          ← 正确是 5,569,903，差了两个数量级
```

所以让模型只写算式，结果由程序算：

```
模型输出：结果是 <calc>6168464619 - 6188669</calc>
程序求值：6162275950（17ms）
```

求值前过正则白名单（`^[0-9eE+\-*/%.()\s]+$`），没有字母就没有函数调用和 `import`。
**这台机器上 bwrap / unshare / docker 全不可用**（user namespace 被禁），做不出真隔离，所以只能靠"能执行的东西本身就没有攻击面"来兜底 —— 这条限制写在 `docs/` 里，不是没考虑到。

### 3. 三层记忆：预算 1100 字，身份永远只由提示词给

| 层 | 内容 | 触发 |
|---|---|---|
| 短期 | 原文 | 最近 4 轮 / 20 分钟，带话题跳变守卫 |
| 中期 | 便签式摘要（≤200 字） | 6 轮或安静 8 分钟 |
| 长期 | `对象｜事实` 表（≤40 条） | 每 4 轮抽取，30 天过期，**只记别人** |

两个细节踩过才知道：

- **话题跳变守卫不能只看词面**。中文短问句的词汇重合度常态就是 0.00~0.09，纯阈值会把正常追问误杀。要"重合度低 **且** 没有指代词"才丢。
- **长期记忆很容易被自己的话污染**。第一版把机器人的回复也喂给抽取器，于是它把"我肚子饿了"记成了用户特征「爱吃辣」。现在只喂 user 消息 + 正则硬拦自称。

### 4. 密钥不落盘，重启即失效

真密钥只有两个（OneBot token、搜索 API key）。它们不在仓库里，也不在算力端磁盘上：

```
主控端 vault（项目目录之外）
      │  node scripts/secrets.mjs push
      ▼
算力端 /run/user/<uid>/qq-bridge.env   ← tmpfs，内存，600
      │
   systemd EnvironmentFile
```

机器重启 → tmpfs 清空 → systemd 找不到文件 → unit 直接 `failed`，**不会带着空 token 假装在跑**。
想要上线就得显式推一次，这就是"授权"。

代价是重启后机器人不会自己回来。这个取舍是故意的，实现里踩了两个 systemd 的坑（见下）。

## 快速开始

零 npm 依赖，只用 Node 内置模块（`node:fs` / `node:path` / `node:crypto` / `node:child_process`）。

```bash
# 1. 配置（仓库里只有 example，真实配置不入库）
cp bridge/config.example.json bridge/config.json

# 2. 密钥：放到项目目录之外的 vault
mkdir -p ~/.secrets && cp .env.example ~/.secrets/qq-bridge.env
$EDITOR ~/.secrets/qq-bridge.env

# 3. 推送到算力端并启动
node scripts/secrets.mjs push --host user@your-gpu-host

# 4. 状态自检
node scripts/secrets.mjs status --host user@your-gpu-host
#    缓存文件 600 : OK
#    unit 指向 tmpfs : OK
#    服务 active : OK

# 5. 不需要 OneBot 也能自测
node bridge/qq-bridge.mjs --selftest
```

需要的服务：Ollama（本地模型）+ 一个 OneBot v11 实现（本项目用 SnowLuma）。

## 踩过的坑

这些是花时间最多的部分，写下来省得重踩。

| 坑 | 真相 |
|---|---|
| **换 `num_ctx` 会触发模型重载** | 同一模型 1024↔4096 交替：判定 4354ms + 主答 5345ms = 9.7s/轮；ctx 一致只要 1.2s/轮。**所有调 Ollama 的进程必须统一 ctx** |
| `EnvironmentFile` 缺失时守卫跑不到 | 环境文件的加载发生在所有 `ExecStartPre` **之前**，所以"缺文件就报错"的守卫必须靠 `-` 前缀把判定权抢回来 |
| `Restart=always` + `RestartSec=5s` 无限重试 | 永远凑不满默认 5 次/10s 的 StartLimit → `is-active` 常驻 `activating`、日志刷屏。StartLimit 要写 `[Unit]`，且要让次数可达 |
| Qwen3 回复为空 | 必须显式 `think:false`，否则 token 全进思考区 |
| 模型偶尔把结果也写进 `<calc>` | `<calc>a - b = c</calc>` 里的 `=` 会被白名单拦掉 → 规则层加"单等号右侧丢弃重算"兜底 |
| 模型"卸载快" | 其实是 32k 时 4% 层溢出到 CPU，`KV_CACHE_TYPE=q8_0` 修好 |
| `pkill -f <字符串>` 杀掉自己的 SSH 会话 | 会匹配到执行命令的 `bash -c` 自身，按 `/proc/*/cmdline` 筛 |
| 多 agent 共写丢功能 | 整份重写时静默丢了两个环境变量 → 之后一律"改前查指纹、只做增量编辑" |

## 已知限制（不美化）

- **4B 撑不住多步算术和长链路推理**。上面那些是补丁，不是修复；真要可靠就得换更大的模型或接确定性工具。
- **没有硬隔离可用**。这台机器 user namespace 被禁，模型生成的代码只能靠白名单软限制，做不到真沙箱。
- **C 档只在文档里回归过**，5 条用例没有在当前环境跑完整回归。
- **重启后需要手动授权**（推密钥）才会上线，这是设计取舍不是 bug。
- 人设偶尔还会用同一个梗收尾 —— 这是 4B 在长上下文里的通病，靠提示词只能压到一定程度。
