## 一、可行性：大脑这一半已经跑通

在 2060 上直接跑 `node qq-bridge.mjs --selftest`（不接 QQ、不接 SnowLuma）：

```
    0ms  [RULE] "你好"                    → 在的，说吧。
    0ms  [RULE] "在吗"                    → 在的，说吧。
 4323ms  [LLM]  "用一句话解释什么是 API。" → API 是应用程序间通信的接口…
  325ms  [LLM]  "今天天气怎么样？"         → 我不确定您所在的具体位置…
  355ms  [LLM]  "Python 里怎么反转列表？"  → 使用切片语法 list[::-1]…
    0ms  [RULE] "你好"                    → 在的，说吧。
```

**结论：**

- 规则命中 **0ms**
- 模型回复 **325~355ms**（预热后稳定）
- 首次 4.3s 是模型冷加载，预热一次即可消除

**剩下的只有 QQ 这半条链路**——需要装 SnowLuma。

## 二、对 SnowLuma 的要求

| 项 | 要求 | 你当前的状态 |
| --- | --- | --- |
| Node.js | `^22.13.0 \|\| >=23.4.0` | ✅ 是 **v24.22.0**，满足 `>=23.4.0`；2026-10-18 已核对 v1.14.22 的 package.json engines |
| 系统 | Linux（有 `launcher.sh`） | ✅ Ubuntu 24.04 |
| 部署形态 | 发行包解压即用（Lite 版需自备 Node） | 待装 |
| WebUI | `http://localhost:5099`，初始密码在启动日志 | 待装 |
| QQ 侧 | 需要一个 **QQ 客户端进程**供其接入（不是扫码网页登录） | 需要小号 |
| 对外接口 | OneBot v11：**正向 WS 服务端**（我们桥接用这个） | 待配 |
| 许可 | **非 OSI 开源，商用需授权**，仅供学习研究 | 注意合规 |
| 端口 | 5099（WebUI）+ OneBot WS（建议 3001） | 注意内网仅本机 |

> Node 24 兼容性结论（2026-10-18）：官方 engines 为 `^22.13.0 || >=23.4.0`，v24.22.0 满足，**不需要降级**。仅当 `launcher.sh` 实际报版本错误时，才考虑用 nvm 装 22 LTS。

## 三、四层调试流程（每层都有明确判定标准）

### L0 · 模型层（已验证 ✅）

```bash
ssh user@192.168.1.20 "cd ~ && node qq-bridge.mjs --selftest"
```

**判定**：规则 0ms、模型 <1s、回答 ≤50 字。
**失败排查**：`ollama ps` 看模型是否在显存；`ollama list` 确认 `qwen3.5:4b-chat` 存在。

### L1 · 桥接层（不需要 QQ）

同上自测即可。这一步验证「上下文裁剪 + 规则前置 + 截断 + 去重」都工作。

### L2 · OneBot 连通（需要 SnowLuma）

1. 解压 SnowLuma 发行包，`chmod +x launcher.sh && ./launcher.sh`
2. 浏览器开 `http://localhost:5099`，用**启动日志里的初始密码**登录
3. 向导里：接入 QQ 进程 → 配置 OneBot 连接 → 选**反向/正向 WS**，端口 `3001`
4. 启动桥：

```bash
ONEBOT_WS=ws://127.0.0.1:3001 node qq-bridge.mjs
```

**判定**：桥的日志出现 `[bridge] OneBot 已连接: ws://127.0.0.1:3001`
**失败排查**：
| 现象 | 原因 |
| --- | --- |
| `ECONNREFUSED 3001` | SnowLuma 的 OneBot WS 没开，或端口不对 |
| 连上但没消息 | 桥监听的是 `post_type=message`；确认 SnowLuma 已上报消息事件 |
| `401/403` | 配了 access_token，需设 `ONEBOT_TOKEN` |

### L3 · QQ 实测（端到端）

用另一个号私聊机器人发「你好」。

**判定**：
- 3 秒内收到回复
- 回复 ≤50 字
- 桥日志打印 `[rule]` 或 `[llm]` 及耗时

**失败排查**：
| 现象 | 原因 |
| --- | --- |
| QQ 里没反应，桥没日志 | OneBot 未上报 → 回 L2 |
| 桥有日志但消息没发出 | `send_msg` 失败，看桥日志里的 action 返回 |
| 群里不回复 | 设计如此：`groupMentionOnly=true`，需 @ |

## 四、常驻运行

```bash
# 简单方式
nohup env ONEBOT_WS=ws://127.0.0.1:3001 node ~/qq-bridge.mjs >> ~/qq-bridge.log 2>&1 &

# 推荐：systemd user service（崩溃自动重启）
mkdir -p ~/.config/systemd/user
cat > ~/.config/systemd/user/qq-bridge.service <<'EOF'
[Unit]
Description=QQ OneBot -> Ollama bridge
After=network.target

[Service]
Environment=ONEBOT_WS=ws://127.0.0.1:3001
ExecStart=/usr/bin/node %h/qq-bridge.mjs
Restart=always
RestartSec=5

[Install]
WantedBy=default.target
EOF
systemctl --user daemon-reload
systemctl --user enable --now qq-bridge
loginctl enable-linger user   # 注销后也保持运行
```

## 五、桥里已经做掉的护栏

| 护栏 | 实现 |
| --- | --- |
| 高频短句 0ms | `RULES` 正则表，命中直接回 |
| 上下文压 prefill | 只带最近 2 轮 + system ≤100 字 + `num_ctx 4096` |
| 防长回答 | `num_predict: 72` + 截断到 50 字（优先断在句号） |
| 关思考 | `think: false`（Qwen3 默认开会吃光 token） |
| 模型常驻 | `keep_alive: -1` |
| 单用户冷却 | 3s（防刷屏） |
| 重复回复抑制 | 同文不重复发 |
| 超时兜底 | 20s 后回「我这边卡住了」 |
| 群聊只 @ | `groupMentionOnly: true` |
| 断线重连 | WS close 后 5s 重连 |
