## 3.5 稳定性复跑（同一任务跑多次）

| 用例 | 第 1 次 | 第 2 次 | 第 3 次 | 正确率 |
| --- | --- | --- | --- | --- |
| 读日志判断状态 | 79s ✅ | 84s ✅ | — | **2/2** |
| 统计日志行数（答案是 1） | 89s ✅ | **69s ❌ 答 0** | 72s ✅ | **2/3** |

**关键发现：同一个任务、同一份数据，第 2 次答了 0（实际是 1）。**

而 69s 比另外两次都快 —— 大概率是**它没真正执行命令，直接凭印象给了个数字**。这是 4B 最危险的失效方式：不报错、不犹豫，安静地给错答案。

已加规则（`task-workspace/AGENTS.md`）：

```
数字 / 计数 / 统计类问题，必须先真的执行命令，并把命令原文和原始输出贴在回答里
（格式：`$ 命令` → `输出`），最后才给结论。不允许凭印象直接给数字。
```

加完第 3 次答对了，但**只有 1 个样本，不能证明是规则的功劳**。

> 结论：**提示词只能降低概率，不能保证。** 对数字类结果，正确做法是在外层用代码复核（模型给命令 + 输出，脚本重跑一遍对账），而不是继续堆提示词。

## 3.7 对账层（已实现：`scripts/task-verify.mjs`）

### 为什么做这个

实测里最坏的一次：同一任务第 2 次答"0"（真值 1），**而且比答对时更快**。后续复现出了根因 —— 它先用**转义错的正则**跑了一遍 `grep -c '\[llm\+search\]'`，命令返回 `0` 且 `exit code 1`，它把这个**失败命令的输出**当成了答案依据。

所以真正的失效模式不是"没执行"，而是**"执行了错的命令，然后相信了它"**。提示词拦不住，只有代码能拦。

### 判据（按优先级）

| 优先级 | 判据 | 说明 |
| --- | --- | --- |
| 1 | `LITERAL_VERIFIED` | 任务里有「统计/行数」意图 + `[字面量]` + 文件路径 → **按字面量直接数一遍**，与答案比对 |
| 2 | `GREP_VERIFIED` | 模型用了 `grep` 工具 → 用 `fs` 独立复算同一个正则 |
| 3 | `MISMATCH` | 上面两者算出真值 ≠ 答案 → 判定失败，附真值 |
| 4 | `NO_TOOL` | 答案含数字但一次工具都没调 → 凭印象答的 |
| 5 | `FROM_FAILED_CMD` | 答案里的数字只出现在**退出码非 0** 的工具输出里 |
| 6 | `CONSISTENT` | 数字能在这个**成功**的工具输出里找到（弱判据，兜底） |
| 7 | `NO_NUMERIC` | 结论不含数字，跳过对账 |

关键修正：最初版本只要"数字出现在任何工具输出里"就算过 —— 那会让"0（来自失败命令）"合法通过。现在**失败输出不再算证据**。

### 判定失败会做什么

把差异告诉模型并重跑一次（`--retries`，默认 1）：

```
【纠正】你上一次的回答是「0」，但工具的实际结果显示 1。请重新执行命令，只按工具的真实输出回答。
```

### 实测证据

| 场景 | 输入 | 判定 |
| --- | --- | --- |
| 真实成功 | `grep` 命中 1，答案 1 | ✓ `LITERAL_VERIFIED`（独立计数 1） |
| **构造失败** | 工具输出 `0 [exit code: 1]`，答案 0 | ✗ `MISMATCH`：独立计数 = 1，答案是 0（退出码 1） |
| 端到端 | 真实跑一遍 | ✓ `PASS`，68s，第 1 次通过 |

### 用法

```bash
# 正常跑（失败自动打回一次）
node scripts/task-verify.mjs "统计 ~/qq-bridge.log 里出现 [llm+search] 的行数，只回答数字。"

# 加一次重试
node scripts/task-verify.mjs "<任务>" --retries 2

# 离线复核一份已保存的 --json 事件（不重新执行任务，用于回归测试判据）
node scripts/task-verify.mjs "<任务>" --audit-only /tmp/run.json
```

退出码：`0` 通过，`1` 未通过，`2` 用法错误。

### 安全边界

**只对 `grep` 工具做独立复算**（纯 `fs` 读取，不执行 shell）。bash 类调用**绝不重跑** —— 因为那是模型生成的命令，重跑等于给它执行权。这条是刻意的取舍：宁可少验一类，也不引入执行风险。

### 局限（别高估它）

1. 只覆盖**可机械复算**的任务（字面量计数、grep）。开放式结论没有对账手段。
2. 任务里没写文件路径时，判据 1 失效，只能退化到一致性检查（弱）。
3. 多轮工具调用只看最终答案里的数字，不校验中间步骤。
4. 它不是"提高模型能力"，只是**把静默错误变成显式失败**。

## 4. 为什么是 80 秒

粗算（结合之前测的 0.6s / 1000 token prefill 与 55 tok/s 生成）：

| 环节 | 估计 |
| --- | --- |
| DSH 基础提示 + 工具清单（几十个工具 schema） | 首轮 prefill 就 3~5 秒起 |
| 多轮工具调用（每轮都要重算上下文） | 3~5 轮 × 数秒 |
| 4B 生成的思考内容（stderr 里能看到推理） | 每轮数百 token |
| 实际命令/检索 | 0.3~2 秒 |

结论：**80 秒里绝大部分是"想"和"读提示"，不是"做"**。这也是它不适合 A 档、但适合 B 档的原因。

## 6. 和原计划的偏差（要说明）

原计划是"**关思考 + 工具 + 校验**"，但实测中 DSH 走的是**开思考**（stderr 有完整推理）。原因是 `agent-default-model` 里不能写 `reasoningEffort`（模型未声明该能力，会报错），而 DSH 默认沿用模型的思考行为。

结果是：**慢，但正确率更高**。对 B 档（不要快）来说这不是坏事，所以暂时不改。

如果以后要提速，唯一有效的杠杆是**减少工具数量**（几十个工具 schema 每轮都进提示），而不是调温度。
