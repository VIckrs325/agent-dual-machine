# 基线测试报告 — 本地 vs 云端

> 2026-10-18 09:35　|　环境：2060 本（RTX2060 6GB / i7-9750H / 32GB）　|　Ollama 0.40.6 + OpenClaw 2026.10.4

---

## 一、测试方法

- 同一组 3 个提示词，分别跑：本地 `qwen3.5:4b`、本地 `ds7b:latest`、云端 `deepseek`（经 OpenClaw 网关）
- 本地：Ollama `/api/generate`，`num_ctx=32768`、`temperature=0.2`、`think=false`、`num_predict=700`
- 云端：`openclaw agent -m "..." --json --session-id baseline-N`（每用例独立会话，排除历史干扰）
- 指标：总耗时、输出 token 数、生成速率、输出可用性（人工判定）

## 五、四个关键发现

### 1. `ds7b` 不适合当 agent 模型，建议退役

- 它**不受 `think=false` 控制**，`<think>` 直接写进正文，700 token 预算全被思考吃光，答案一个没出。
- 思考质量也差：把「100MB = 10G」算错，说明这个自建模型的量化/微调有问题。
- 结论：**换 `qwen3.5:4b`，别在 ds7b 上继续投入。**

### 2. OpenClaw 每轮基础开销 ≈ 10,861 tokens（这是硬约束）

- 全新会话问「hi」，输入就是 **10,861 tokens**（system prompt + 技能 + 工具清单）。
- 主会话那次是 73,692 tokens，因为堆了历史。
- **推论：本地模型 `num_ctx` 必须 ≥ 16384，否则连基础提示都装不下，会被截断成乱码。**

### 3. 当前 Ollama 默认上下文是 4096 —— 直接接入 OpenClaw 必然失败

| 模型 | 实际 num_ctx | 面对 10.9k 基础提示 |
| --- | --- | --- |
| `ds7b` | **4,096（Modelfile 写死）** | ❌ 截断 |
| `qwen3.5:4b` | 4,096（Ollama 服务默认，未设 `OLLAMA_CONTEXT_LENGTH`） | ❌ 截断 |

这解释了为什么"本地接进去效果差"——不是模型不行，是**上下文被砍了 60%**。

### 4. 云端与本地在简单任务上差距已很小，复杂解释类仍云端更强

- 01 / 03：本地 2.7~3.2s vs 云端 2.6~3.1s，**基本打平**，质量都可用。
- 02：云端 5.5s 给出更准确、更有结构的答案；本地 16.3s 且啰嗦到截断。
- 结论：**简单确定性任务→本地；需要准确解释/多方案比较→云端。**

## 六、建议的落地改动（P0）

### 1) 把 Ollama 默认上下文提到 32k（必须）

```bash
# 方案 A：改服务环境（推荐，全局生效）
sudo systemctl edit ollama --force <<'EOF'
[Service]
Environment="OLLAMA_CONTEXT_LENGTH=32768"
Environment="OLLAMA_MAX_LOADED_MODELS=1"
Environment="OLLAMA_KEEP_ALIVE=-1"
EOF
sudo systemctl daemon-reload && sudo systemctl restart ollama
```

```bash
# 方案 B：不动服务，做一个 32k 专用变体（无需 sudo）
printf 'FROM qwen3.5:4b\nPARAMETER num_ctx 32768\n' > /tmp/q35-32k.Modelfile
ollama create qwen3.5:4b-32k -f /tmp/q35-32k.Modelfile
```

> `MAX_LOADED_MODELS=1` 是防止 qwen 和 ds7b 同时占显存导致 OOM（32k 下两者合计会超 6GB）。

### 2) 本地主力模型换成 `qwen3.5:4b`

- `ds7b` 退役（保留文件不删，仅不再配置进 OpenClaw）。
- 简单任务 `think=false`（快 2~3 倍）；复杂推理再开 `think=true`。

### 3) 接入 OpenClaw 时的参数

| 参数 | 建议值 | 理由 |
| --- | --- | --- |
| `contextWindow` | 16384（最低）/ 32768（推荐） | 基础提示 10.9k + 任务余量 |
| `maxTokens` | 2048 | 4B 模型长输出易跑偏 |
| `requiresStringContent` | true | 本地后端兼容 |
| 默认路由 | 简单任务本地、解释/多方案走云端 | 见第五节第 4 条 |

## 七、对 `docs/04` 的修正

原文建议「num_ctx 默认 8192」——**在 OpenClaw 场景下这是错的**，8k 装不下 10.9k 基础提示。

修正为：

- **直连 Ollama API（不经 OpenClaw）**：8192 够用。
- **经 OpenClaw agent 调用**：**最低 16384，推荐 32768**。

## 八、补充：原版 R1 两个模型（09:50 补测）

| 模型 | 32k 速度 | 700 token 预算 | 2,500 token 预算 |
| --- | --- | --- | --- |
| `deepseek-r1:7b`（原版） | 14.3 tok/s | ❌ 无正文 | ⚠️ 132.0s 才出答案，`</think>` 前有 **4,299 字符**思考 |
| Q3_K_M（bartowski） | 19.0 tok/s | ❌ 无正文 | ⚠️ 42.2s 出答案，思考 **1,523 字符** |

**判定：不是"不会答"，是"话太多"。** 给足预算都能出正确答案，但 7B distill 的思考长度使单次任务耗时 42~132 秒，不适合交互。

`think: false` 对这两个模型无效（`<think>` 当正文输出），只有 `qwen3.5:4b` 支持真正的 thinking 开关。
