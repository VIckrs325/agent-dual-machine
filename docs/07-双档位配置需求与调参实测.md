# 双档位配置需求与调参实测

> 2026-10-18 10:40　|　模型：qwen3.5:4b（4.2B / Q4_K_M）　|　硬件：RTX2060 6GB，32k 全显存（KV q8_0）

---

## 一、需求记录（原文与拆解）

### A 档：快速聊天机器人

> 「快速回复并且其他性能堪用的聊天型机器人，每次回答 50 字以内，不需要深度思考」

拆成可测指标：

| 指标 | 目标 |
| --- | --- |
| 首字/整轮时延 | < 1.5s |
| 单条回答长度 | ≤ 50 字 |
| 稳定性 | 同类问题多次回答不跑偏、不空答 |
| 思考 | 关闭 |

### B 档：深度思考本地执行助手

> 「有深度思考，在本地执行简单任务的助手，能联网收集信息，注重执行的稳定与准确，对时间要求不高」

| 指标 | 目标 |
| --- | --- |
| 正确率/稳定性 | 优先（可接受长时间等待） |
| 工具执行 | 能跑本地命令、读文件 |
| 联网 | 能抓取网页/接口信息 |
| 思考 | 开启 |

## 二、实测数据

### 2.1 A 档：有无字数指令的差别（think=false）

| 问题 | 无指令、n=96 | 有指令、n=64（temp 0.3） |
| --- | --- | --- |
| 事实（首都） | 0.1s / 2 字 | — |
| 闲聊 | 1.3s / **122 字** ❌ | **0.3s / 24 字** ✅ |
| 字数约束（≤20 字） | 0.3s / 22 字 | 0.3s / 23 字 |
| 代码 | 0.3s / 29 字 | — |
| 算术 | 0.1s / 2 字 | — |

**结论：字数靠「指令」控制，不靠参数。** 同一句闲聊，无指令 122 字，加「请用 50 字以内回答」后 24 字。

### 2.2 temperature 对 A 档的影响

| temp | 时延 | 长度 | 两次回答是否相同 |
| --- | --- | --- | --- |
| 0.2 | 0.4s | 24 字 | 不同 |
| 0.5 | 0.3s | 22 字 | 不同 |
| 0.8 | 0.4s | 28 字 | 不同 |

**结论：temperature 对时延无影响；0.2~0.8 都稳定可控。聊天建议 0.4（有点变化但不发散），追求一致性用 0.2。**

### 2.3 B 档：开启思考后的问题（think=true, temp=0.2）

| 问题 | 时延 | 思考长度 | 是否给出答案 |
| --- | --- | --- | --- |
| 事实 | 3.4s | 584 字符 | ✅ 北京 |
| 闲聊 | 16.2s | 2,622 字符 | ✅（想聊天想了 2600 字） |
| 字数约束 | 48.2s（n=2500） | 5,635 字符 | ❌ **输出为空，done=length** |
| 代码 | 2.8s | 234 字符 | ✅ |
| 多步命令 | 25.9s | 4,661 字符 | ✅ 与关闭思考的结果**完全一致** |
| 字数约束（派生模型 n=4096） | 87.7s | 8,831 字符 | ❌ **仍为空** |

**三个结论：**

1. **思考没有带来质量提升**：多步命令任务，开启/关闭思考给出的是同一行命令，但耗时 0.5s → 25.9s（50 倍）。
2. **思考会失控**：简单题也可能想 8831 字符，把 4096 的输出预算全吃光，最终 `done=length` 且正文为空。这是**不可接受的稳定性问题**。
3. **B 档「深度思考」在 4B 上不成立**，不是参数没调好，是模型本身的行为特征。

### 2.4 已创建的两个派生模型（磁盘几乎零增量）

```bash
ollama create qwen3.5:4b-chat -f /tmp/chat.Modelfile   # temp0.4 top_p0.9 num_predict72 num_ctx16384
```

## 三、推荐配置

### A 档（快速聊天）

| 参数 | 值 | 理由 |
| --- | --- | --- |
| 模型 | `qwen3.5:4b-chat` | 参数已固化 |
| think | **false** | 关掉才有 0.3s 级响应 |
| temperature | 0.4 | 聊天不呆板，仍可控 |
| num_predict | 72 | 约对应 100+ 字上限（**token 不能精确控字数**） |
| num_ctx | 16384 | 聊天够用，KV 更小、prefill 更快 |
| **系统指令** | 「回答控制在 50 字以内，不分点、不寒暄」 | **这条是达成 50 字的关键** |

> ⚠️ `num_predict` 按 **token** 计，72 token 实测出来 123 个汉字。要严格 ≤50 字，必须靠指令，并在应用层做长度截断（超过就截到句号）。

### B 档（任务执行）

| 参数 | 值 | 理由 |
| --- | --- | --- |
| 模型 | `qwen3.5:4b`（或 `-deep`） | |
| think | **建议 false**；需要时再开 | 开思考不提升正确率且可能空答 |
| temperature | 0.2 | 稳定优先 |
| num_predict | 2048~4096 | 给足输出空间，防截断 |
| num_ctx | 32768 | 容纳工具返回的长文本（网页、文件） |
| 工具 | bash + 文件读写 | 本地执行 |
| 联网 | 由 bash 执行 `curl` / `python -c requests` | 见第五节 |

**若坚持要「深度思考」：改走云端。** 这正是原方案「复杂任务路由云端」的价值——4B 开思考既慢又不可靠，云端 deepseek 一条就够。

## 四、落地到 DSH 的两套档位

DSH 的思考开关、指令文件都在 profile 层，所以建议**双 profile**：

| | `chat` profile | `task` profile |
| --- | --- | --- |
| 模型 | `ollama/qwen3.5:4b-chat` | `ollama/qwen3.5:4b` |
| 指令文件 | 工作区 `AGENTS.md`：50 字以内、口语化、不寒暄 | 工作区 `AGENTS.md`：先给结论、命令需可执行、不确定就说不确定 |
| 工具 | 关闭 bash（纯聊天，更安全更快） | 开启 bash + 文件读写 |
| 思考 | 关闭 | 默认关，必要时手动开 |

指令注入机制（已从 schema 确认）：`@deepseek-ai/dsh-agent-instructions` 插件按 `instructionFileCandidates` 从**工作区根目录**读取指令文件（默认含 `AGENTS.md` 一类）。所以每条档位的「人设」写在各自工作区的 `AGENTS.md` 里，不需要改代码。

```bash
# 建两个 profile
npx -y @deepseek-ai/dsh --from-default-profile web --profile chat
npx -y @deepseek-ai/dsh --from-default-profile web --profile task
# 各自 cordis.patch.yml 里指不同模型；各自工作区放不同 AGENTS.md
```

## 五、联网能力的实现路径

DSH 本身不带搜索插件，但有三条现成路：

| 方式 | 做法 | 适用 |
| --- | --- | --- |
| **bash + curl**（推荐起步） | `curl -s "https://api.example.com/..."`，agent 自己解析 | 抓接口、取网页正文 |
| python + requests | `python3 -c "import requests;..."` | 需要解析 JSON/HTML |
| 第三方插件 | `dsh plugin --profile task add ...`（社区有 ollama/搜索类插件） | 需要搜索摘要、多页聚合 |

> 关键点：**联网能力来自「工具」，不是来自模型**。模型不会自己上网，必须让它调用 bash/curl 或插件。4B 的工具选择准确率一般，所以 B 档的工具集要保持在 3~5 个以内。

## 六、总体结论

1. **A 档可以做得很好**：0.3s 级响应、字数靠指令控制。**唯一残留问题是「50 字」需应用层兜底截断**，模型只能逼近不能保证。
2. **B 档的「深度思考」在 4B 上是伪需求**：开思考不加分、可能空答、慢 50 倍。正确的 B 档 = **关思考 + 工具 + 结构化提示 + 结果校验**；真正需要深推理的任务路由云端。
3. **参数层面已经收敛**：时延主要由「是否开思考」决定，temperature/num_ctx 影响很小。所以调参的重点不在数值，而在**开关与指令**。
