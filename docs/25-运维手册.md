## 2. 四条主线

### A 档：快速聊天（≤50 字、不思考）

- 模型：`qwen3.5:4b-chat`（Modelfile 烧了 num_predict 72 / temp 0.4 / top_p 0.9 / presence_penalty 1.5）
  - **ctx 注意**：Modelfile 里烧的是 `num_ctx 16384`，但桥每次请求都显式传 `num_ctx: 4096`（`DEFAULTS.numCtx`）把它覆盖掉，`ollama ps` 的 CONTEXT 也显示 4096 —— **实际生效的是 4096**，不是 16384
- 人设：工作区 `chat-workspace/AGENTS.md`
- 实测：5 个常见问题 **5/5 ≤50 字，平均 0.31s**
- 启动：`npx -y @deepseek-ai/dsh --profile chat`

### B 档：搜索 + 总结（`btask/`）

- 模型：`qwen3.5:4b`（默认关思考），流水线 = 规划 → 检索 → 压缩 → 核查 → 补充 → 总结
- 四档：`--profile quick|smoke|plan|deep`（8~350s）；`--dry-run` 只解析、不调模型
- 边界：**碰不到本机**；实时数值与精确算术都不可靠 → `btask/CAPABILITY.md`
- 启动：`node btask/run.mjs "问题" --profile quick`

### C 档：会动手的任务执行（`ctask/`）

- 模型：`qwen3.5:4b` + 工具调用（DSH `headless` profile），单任务实测 185s
- 能：读文件 / 写文件 / 执行命令 / 多步串行 —— B 档做不了的事都在这一档
- 对账层：数字类任务必须走 `scripts/task-verify.mjs`，用代码复核，而不是信模型
- 结论：**不要用 7B R1 做执行**（命令全错）；14B IQ2_M 只在离线兜底时考虑
- 启动：`bash scripts/b-task-baseline.sh [id]`，或用例详情见 `ctask/README.md`

### QQ 机器人（SnowLuma + 极简桥）

```
QQ → SnowLuma(OneBot v11 WS:3001) → qq-bridge.mjs → Ollama(127.0.0.1:11434)
                                          ↑
                                  规则层先过（0ms）
```

- 桥：零依赖 Node，只处理 `post_type=message`，直连 Ollama
- 实测：规则 **0ms**，模型 **325~355ms**（预热后），首次冷加载 4.3s

## 3. 桥怎么跑

**生产环境由 systemd 托管（唯一方式）**，不要再用 `nohup` 手动起：

```bash
systemctl --user status  qq-bridge     # 看状态
systemctl --user restart qq-bridge     # 改完代码重启
journalctl --user -u qq-bridge -f      # 看日志（比 ~/qq-bridge.log 更全）
systemctl --user disable --now qq-bridge   # 停用
```

```bash
# 自测（不需要 SnowLuma / QQ，也不占实例锁）
ssh user@192.168.1.20 "cd ~/.openclaw/workspace/projects/agent-dual-machine/bridge && node qq-bridge.mjs --selftest"
```

`run-bridge.sh` 现在**检测到服务在跑会直接拒绝（exit 2）**，只用于临时调试；`--selftest` 不受影响。

> 服务单元：`~/.config/systemd/user/qq-bridge.service`（`Restart=always`、`ExecStart` 直连 node、`EnvironmentFile=/run/user/<uid>/qq-bridge.env`）。密钥放在 tmpfs 上，由主控端 `node scripts/secrets.mjs push` 推入，**不落盘、重启即失效**。已 `enable-linger`，但密钥文件重启后不存在，需要重新推一次才会重新上线。

### 运行时产生的两个文件

| 文件 | 作用 |
| --- | --- |
| `bridge/.bridge.pid` | 单实例锁，防两个桥同时连 OneBot |
| `bridge/.state.json` | **会话存档**（权限 600），重启后恢复最近 30 分钟的对话 |

### 热重载（v2 起支持）

桥把参数放在 `bridge/config.json`，**改完自动生效，进程不重启、WS 不断**：

```bash
# 直接编辑，2 秒内生效；日志会打印 [reload] maxChars=50→100
vim ~/.openclaw/workspace/projects/agent-dual-machine/bridge/config.json
# 或手动触发
kill -HUP <bridge-pid>
```

**不放回答长度到 100 字**，只改三个字段：

```json
"maxChars": 100,
"numPredict": 150,
"system": "你是聊天助手。规则：每次回答不超过100字；不分点、不加标题、不寒暄。"
```

实测：`numPredict 150` 时，84 字回答耗时 943ms。

### 各层热重载能力对照

| 层 | 支持 | 说明 |
| --- | --- | --- |
| 桥（config.json） | ✅ 热重载 | 文件变更自动生效 / `kill -HUP` |
| SnowLuma（WebUI） | ⚠️ 部分 | 改 OneBot 配置即时生效；换版本要重启 |
| 模型请求参数 | ✅ 随桥配置 | `num_predict` / `temperature` 每次请求都从 CFG 读 |
| Modelfile 固化参数 | ❌ | 要 `ollama create` 重建模型才变 |
| `ollama serve` 环境变量 | ❌ | 改 `KEEP_ALIVE`/`CTX` 必须 `systemctl restart ollama` |
| DSH profile | ❌ | 改 `cordis.patch.yml` 必须重启 dsh |

### 桥里已内置的护栏

| 护栏 | 实现 |
| --- | --- |
| 高频短句 0ms | 正则规则表（你好/在吗/谢谢/再见） |
| 压 prefill | 只带最近 2 轮 + system ≤100 字 + `num_ctx 4096` |
| 防长回答 | `num_predict 72` + 截断 50 字（优先断句号） |
| 关思考 | `think:false`（Qwen3 默认开会吃光 token） |
| 模型常驻 | `keep_alive:-1` |
| 防刷屏 | 单用户 3s 冷却 + 同文抑制 |
| **单实例** | `.bridge.pid` 锁，重复启动直接退出（防两个桥同时连 OneBot 双回复） |
| **事件去重** | 同 `message_id` 60s 内只处理一次（重连/重投递） |
| **回复去重** | 同用户 15s 内产生相同回答则不发 |
| **并发保护** | 同用户上一条未答完时丢弃新消息，避免叠加 |
| **会话保持** | 对话落盘 `.state.json`，重启/服务重启后接着聊（TTL 30min） |
| **常驻** | systemd `Restart=always` + linger，崩溃自动拉起、注销不断 |
| 超时兜底 | 20s 回「我这边卡住了」 |
| 群聊 | 只在被 @ 时回复 |
| 断线 | WS close 后 5s 重连 |
| **联网搜索** | 规则判定是否搜（显式指令 / 时效+疑问），检索词自动清洗，结果编号注入并要求标 `[n]`，资料不足只能回「没查到」 |

## 6. 多 agent 协作纪律（防互相覆盖）

这个工程同时有 **WorkBuddy（我）** 和 **2060 上的 OpenClaw** 在改，共享文件一律按下面走：

```bash
# 1) 动手前：查指纹
node scripts/file-guard.mjs check bridge/search.mjs
#    CLEAN → 可以改；DRIFT → 别人改过，先读最新内容再合并；UNTRACKED → 新文件，随便写

# 2) 改：已存在的文件只用增量编辑（Edit），禁止整份重写

# 3) 留痕：CHANGELOG.md 的「进行中」认领 → 完工移入「变更记录」→ 盖章
node scripts/file-guard.mjs stamp --by workbuddy
```

- **`CHANGELOG.md`** 是施工公告板：谁在改什么、改了什么、怎么验证，都在那儿。
- **`scripts/file-guard.mjs`** 是守卫：用 sha256 记住每个文件的内容指纹，`check` 能立刻告诉你有没有人动过。
- **`scripts/check-runtime-units.mjs`** 检查 systemd unit / drop-in：稳定服务必须指向 `bridge/`，不能有 active drop-in；`--runtime` 还会核对 MainPID、ExecStart 和锁文件。
- 运行时文件（`.state.json`、`.bridge.pid`、`*.log`）不入账。

> 这条纪律是被真实事故逼出来的：桥 v2 整份重写时，静默丢了 `OLLAMA_URL`/`SYSTEM` 两个环境变量，
> 直到用户问"继承功能呢"才发现。指纹 + 公告板能挡住这类覆盖。

## 7. 踩过的坑（省得重踩）

| 坑 | 教训 |
| --- | --- |
| DSH 报 `no adapter registered` | 自定义 provider 必须挂 **`llm-pi-ai`**，不是 `dsh-llm` |
| DSH 报 `does not support reasoning effort` | 手工声明的模型只支持 `off`；`low` 会被拒 |
| DSH 报 `No API key for provider` | 加 `headers.Authorization` 即可绕过（本地服务不校验） |
| Qwen3 回复为空 | 必须显式 `think:false`，否则 token 全进思考区 |
| 模型"卸载快" | 其实是 32k 时 4% 层溢出到 CPU；`KV_CACHE_TYPE=q8_0` 修好 |
| 手改 `workspace.json` 导致工作区全崩 | 表 + `workspaceIds` 两个真源必须同步，优先用 UI 建 |
| `pkill -f dsh` 杀掉了自己的 SSH 会话 | 按端口找 PID，别按命令行匹配 |
