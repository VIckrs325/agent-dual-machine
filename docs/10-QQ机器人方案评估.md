# QQ 机器人方案评估（SnowLuma + 本地模型）

> 2026-10-18 11:40

---

## 一、先厘清三个组件的定位

| 组件 | 本质 | 能做什么 | 缺什么 |
| --- | --- | --- | --- |
| **SnowLuma** | QQ ↔ **OneBot v11** 的协议转换运行时 | 把 QQ 消息变成标准事件；提供 WS / HTTP / WebUI / SDK / **MCP** | 它只是**管道**，不含 bot 逻辑、不含模型 |
| **DSH** | 交互式 Agent harness（Web UI） | 人对着界面聊、跑任务、调 prompt | **没有消息入口**、没有"外部事件触发会话"、API 未文档化 |
| **OpenClaw** | Agent 网关 + 通道/工具编排 | 多通道、工具调用、云端模型、`agent -m` 非交互入口、`mcp` 管理 | **没有 QQ 原生通道**（channel 列表里无 qq） |

**结论：DSH 不适合当 QQ 机器人的后端。**

原因很具体：

1. DSH 的触发是「用户在 UI 里发消息」，没有「OneBot 事件 → 新会话」的入口；
2. 它的 HTTP 接口是内部的 typert gateway，没有公开文档，桥接等于逆向；
3. 它是常驻的单用户交互台，会话/审批/UI 状态强耦合，不适合当服务端；
4. 它没有主动推送能力（bot 需要主动发消息）。

**SnowLuma 也是半成品管道**——它把 QQ 变成 OneBot 事件流，但**消费这些事件的"大脑"要另外选**。

## 二、三种可行方案

| | 方案 1：OneBot 框架（推荐） | 方案 2：自写桥 | 方案 3：OpenClaw 当大脑 |
| --- | --- | --- | --- |
| 组成 | SnowLuma + AstrBot/NoneBot/MaiBot | SnowLuma + 自写 Node/Python 桥 → Ollama | SnowLuma MCP + OpenClaw |
| 模型接入 | 框架里填 OpenAI 兼容地址，直连 Ollama | 直接调 `/api/chat` | OpenClaw 的 provider |
| 工作量 | **1~2 小时** | 半天（自己维护） | 1~2 天（入站桥仍要写） |
| 会话/限流/人设 | 框架自带 | 自己写 | OpenClaw 自带 |
| 用不用 DSH | 不用 | 不用 | 不用 |

### 方案 1 最小配置（推荐）

```yaml
# AstrBot 里新增 OpenAI 兼容 provider
api_base: http://127.0.0.1:11434/v1
api_key : ollama            # 本地不校验，随便填
model   : qwen3.5:4b-chat   # 用我们调好的聊天档（temp0.4 / n_predict72）
```

`qwen3.5:4b-chat` 已经把「短回答、不啰嗦」的参数固化在模型里，再配合系统提示「回答不超过 50 字」，就是你要的 A 档机器人。

### 方案 2 的核心逻辑（约 80 行）

```
OneBot WS 收到 message 事件
  → 过滤：仅私聊 / 群聊需 @
  → 拼上下文（最近 3 轮 + 人设）
  → POST http://127.0.0.1:11434/api/chat  (model=qwen3.5:4b-chat, think=false)
  → 取 message.content，截断到 50 字
  → 调 OneBot 动作 send_msg
```

关键点：**去重 + 限流**（同一用户 3 秒内只回一次），否则模型偶发重复会导致刷屏。

## 三、还需要做什么（清单）

| # | 事项 | 说明 |
| --- | --- | --- |
| 1 | **准备 QQ 小号** | 机器人有风控/封号风险，**不要用主号** |
| 2 | 装 SnowLuma | Linux 发行包 + `launcher.sh`；需 Node 22.13+（2060 已是 22.x） |
| 3 | 首次配置 | 开 `http://localhost:5099`，用启动日志里的初始密码登录，接 QQ 进程、配 OneBot 连接 |
| 4 | 选方案并搭"大脑" | 方案 1 最快；方案 2 最可控 |
| 5 | 人设复用 | 直接搬 `chat-workspace/AGENTS.md` 的规则（50 字、不寒暄） |
| 6 | 限流/去重 | 单用户冷却 3s、同文去重、每日上限 |
| 7 | 失败兜底 | 模型超时（>20s）回「稍等，我卡住了」，别静默 |
| 8 | 日志 | 记录每条输入输出，便于调 prompt |

## 四、风险与合规（必须知道）

1. **SnowLuma 与腾讯无隶属关系**，非 OSI 开源许可，**商业使用需授权**，仅供学习研究。
2. **QQ 机器人存在封号风险**，这是协议实现的固有风险，不是配置问题。
3. 群里必须**只在被 @ 时回复**，否则刷屏会被踢、被举报。
4. 别把 API key、内网地址暴露在机器人回复里（模型可能复述上下文）。

## 五、我的建议

**用方案 1，把 DSH 留在"调试台"的位置。**

工作流是：

```
DSH（chat profile）  →  调人设、试参数、看效果
        ↓ 人设/参数定稿
AstrBot + SnowLuma  →  正式跑 QQ 机器人
        ↑
Ollama qwen3.5:4b-chat（同一份模型，参数已固化）
```

理由：DSH 的强项是"人和模型对话的调试体验"，不是"7×24 的消息服务"。把它塞进消息链路，等于用一个带 UI 的交互工具去做守护进程——能跑，但脆。

而模型本身（`qwen3.5:4b-chat`）已经调好了，**谁调用都一样的输出**——所以调试台和服务端分开，互不影响。

---

## 六、如果一定要让 DSH 参与

只有一种合理方式：**把 DSH 当作"人设与参数的试验田"**，而不是运行时。

- 在 DSH 里试不同 AGENTS.md 的措辞
- 定稿后把同一份 AGENTS.md 拷给 AstrBot 的系统提示
- 正式链路完全不依赖 DSH

这样既用上了 DSH，又不引入脆弱性。
