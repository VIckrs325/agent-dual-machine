# Qwen3-14B IQ2_M 可用性评估

> 2026-10-18 11:15　|　模型：`hf.co/liodon-ai/Qwen3-14B-Base-imatrix-GGUF:IQ2_M`
> 14.8B / **IQ2_M（2-bit）** / 5.3GB / 原生 ctx 32768

---

## 一、最要紧的一条：这是 **Base** 模型，不是 Instruct

模型名里的 `Qwen3-14B-Base` 说明它是**预训练基座**，没有做指令微调。

- Base 模型的行为是「续写文本」，不是「回答问题」
- 所以它不会自己停下来 —— 输出越长越容易跑偏、开始模仿前文的格式复读
- 这正是你观察到的「容易进循环」的**根本原因**，不是参数没调好

**建议优先换成 `Qwen3-14B-Instruct` 的 GGUF**（同样 IQ2_M 或 IQ3_M）。这一条比任何调参都有效。

## 二、实测数据

### 2.1 三个任务的表现

| 任务 | 时延 | 输出 | 判定 |
| --- | --- | --- | --- |
| 查找 >100MB 文件命令 | 28.9s | `find . -type f -size +100M -ls \| sort -k5n \| tac` | ✅ **正确** |
| 读 JSON 求 a 字段和 | 6.0s | `sum(item['a'] for item in data)` | ❌ 误判 data 为列表（实为 dict） |
| 自我介绍 | 9.8s | 正常、连贯 | ✅ |

> 命令题它答对了 —— 这点比 7B R1 强（7B 的三种配置全错）。

### 2.2 性能

| 项 | 实测 |
| --- | --- |
| 生成速率 | **7~8 tok/s** |
| 分层 | **29% / 71% CPU/GPU**（5.3GB 权重塞不进 6GB） |
| ctx 4096 vs 8192 | 7.5 vs 6.6 tok/s（差别不大，CPU 卸载是主因） |
| 一次问答墙钟 | 20~50 秒 |

### 2.3 循环诱导测试（「列 30 个 Linux 命令」）

| 参数 | 时延 | 结果 | 循环 |
| --- | --- | --- | --- |
| temp0.7 / rp1.0 | 52.5s | 694 字，干净清单 | 重复行 2 次，无退化 |
| **temp0.3 / rp1.2** | 89.8s | `done=length`，尾部出现「。，请提取关键信息形成概要」然后重新开列 | **重复行 5 次，开始退化** |
| **temp0.6 / rp1.05** | 48.1s | 539 字，干净清单（到 21 条被 token 上限截断） | **重复行 1 次，无退化** |

**反直觉结论：把 `repeat_penalty` 调高（1.2）+ 温度调低（0.3）反而更容易退化。** 高惩罚会破坏正常的重复词（如 Markdown 的 `**`、命令名），模型被迫换词，进而滑向无意义复读。

## 三、防循环的六条（按有效性排序）

| # | 手段 | 说明 |
| --- | --- | --- |
| **1** | **换 Instruct 版** | 根因；Base 模型天生不会收尾 |
| **2** | `num_predict` 封顶 320~400 | 到上限即截断，不给它"跑偏"的空间 |
| **3** | `repeat_penalty` 1.05~1.10 | **不要 ≥1.15**，实测 1.2 更差 |
| **4** | `temperature` 0.6 左右 | 低于 0.4 容易锁死在同一个 token 路径 |
| **5** | 输出后处理去重 | 检测到连续 3 行重复就截断并重试（应用层护栏） |
| **6** | 加 stop 序列 | 如以 ```` ``` ```` 结尾的任务，用 `\n```\n` 作停止符 |

## 四、可用性判定

| 维度 | 评价 |
| --- | --- |
| 正确性 | 中上 —— 简单命令题能答对，复杂结构会误判 |
| 速度 | 差 —— 7 tok/s，一次问答 20~50s |
| 稳定性 | 中 —— 短答稳定，长答需护栏 |
| 适用 | **B 档（对时间不敏感）**，且必须配 num_predict 上限 |

### 与其它模型的定位对比

| 模型 | 速度 | 命令题正确性 | 适合 |
| --- | --- | --- | --- |
| `qwen3.5:4b` | **55 tok/s** | ✅ 正确、0.5s | A 档主力 + B 档主力 |
| 14B IQ2_M（Base） | 7 tok/s | ✅ 正确、29s | B 档备选（离线/隐私） |
| 7B R1（3 种配置） | 20~30 tok/s | ❌ 全错 | 不建议用 |

**结论：14B IQ2_M 比 7B R1 强（至少答对了），但仍远不如 4B qwen3.5 实用。**
它的价值在于「参数大、2-bit 也能塞进 6GB」，适合当 **B 档的离线兜底**；
日常主力还应是 `qwen3.5:4b` + 校验 + 云端兜底。

## 五、如果要正式启用

```bash
# 建议做一个护栏版派生模型
cat > /tmp/q14-task.Modelfile <<'EOF'
FROM hf.co/liodon-ai/Qwen3-14B-Base-imatrix-GGUF:IQ2_M
PARAMETER temperature 0.6
PARAMETER repeat_penalty 1.05
PARAMETER num_predict 384
PARAMETER num_ctx 8192
EOF
ollama create q14-task -f /tmp/q14-task.Modelfile
```

> 注意 `num_ctx` 给 8192 就够：14B 的权重已经占满显存，ctx 再大只会让 KV 也挤到 CPU，速度更差、收益很小。

## 六、补充实测：q14-task 派生模型 + 一个必知的陷阱

### 6.1 陷阱：Qwen3 默认开思考，会导致「正文为空」

创建 `q14-task` 后第一次复测，出现 **58.8s、`done=length`、正文完全为空**。

原因不是模型坏了，是我调用时漏了 `think: false`：Qwen3 系列默认开启思考，24/384 个 token 全进了思考区，`response` 自然是空串。

> **凡是 Qwen3 系模型，API 调用必须显式传 `think: false`**，否则会看到"跑了很久但没输出"。
> DSH 侧同理——这也可能是你觉得"像在循环"的一部分原因。

### 6.2 加上 think:false 后的复测

| 提示 | 时延 | 结果 |
| --- | --- | --- |
| 「只回复两个字：收到」 | 9.0s | ❌ 回了 121 字的说教，`done=length` |
| 查找 >100MB 文件命令 | 36.1s | ❌ `find . -type f -size +100M \| sort -k2 -nr \| cut -d' ' -f2`（排序字段无意义） |

### 6.3 一个更要紧的发现：正确性不稳定

同一个命令题：

- 基线（temp0.7 / rp1.0）：`find . -type f -size +100M -ls | sort -k5n | tac` → **对**
- 护栏版（temp0.6 / rp1.05）：`find ... | sort -k2 -nr | cut ...` → **错**

**参数微调就能让答案从对变错**，说明它的正确性靠运气，不是靠能力。

## 七、最终判定

**不建议把 14B IQ2_M（Base 版）作为 B 档主力。**

| 问题 | 严重程度 |
| --- | --- |
| Base 模型不遵循指令（让它说"收到"却说了 121 字） | 严重 |
| 正确性不稳定（同题两种参数一对一错） | 严重 |
| 速度 7 tok/s，单次 20~60s | 可接受（B 档不在意时间） |
| 需要人工护栏（think:false、num_predict 上限、去重） | 中等 |

**正确做法**：换成 `Qwen3-14B-Instruct` 的 IQ2_M/IQ3_M。
若只想在现有模型上将就，那它更适合「离线兜底」而不是「日常主力」——
日常仍推荐 `qwen3.5:4b`（55 tok/s、指令跟随好）+ 校验层 + 云端兜底。
