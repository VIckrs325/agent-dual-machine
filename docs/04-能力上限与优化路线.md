# 能力上限分析与优化路线

> 2026-10-18　|　基于 2060 本（RTX2060 6GB / 32GB RAM / ds7b）实测数据

---

## 一、先纠正一个前提：显存不是唯一瓶颈

把「6G 显存」当成唯一瓶颈，会优化错方向。这里其实是**四个不同的天花板**，各自有不同杠杆：

| # | 天花板 | 真实约束 | 有效杠杆 | 能否靠"提示词"解决 |
| --- | --- | --- | --- | --- |
| 1 | **上下文长度** | KV cache 占用显存 | `num_ctx` 调高、KV 量化、分层 offload | ❌ 无效 |
| 2 | **推理深度** | 7B 参数容量 | 换更大模型 / 路由到云端 | ⚠️ 只能小幅改善 |
| 3 | **吞吐（首字延迟）** | prefill 是**算力**瓶颈，不是显存 | 缩短输入、prefix cache、减少无关上下文 | ✅ 有效 |
| 4 | **输出可靠性** | 幻觉、格式错、工具调用错 | **后处理校验层** | ✅ **最有效** |

所以你问的「预处理 + 后处理 + 联网搜索」，真正主攻的是 **3 和 4**，对 1 有间接帮助（减少上下文需求），对 2 基本无能为力。

## 二、你的真实上下文上限（实测）

同一模型 `ds7b:latest`，只改 `num_ctx`，其余不变：

| num_ctx | 生成速率 | 进程占用显存 | GPU 总占用 | 状态 |
| --- | --- | --- | --- | --- |
| 4,096 | 29.8 tok/s | 3,574 MB | 4,034 MiB | ✅ 全显存 |
| 8,192 | 30.1 tok/s | 3,790 MB | 4,250 MiB | ✅ 全显存 |
| **16,384** | **30.1 tok/s** | **4,242 MB** | **4,686 MiB** | ✅ **全显存，推荐** |
| 32,768 | 28.9 tok/s | 5,097 MB | 5,544 MiB | ⚠️ 部分溢出到内存，仍可用 |
| 65,536 | — | — | — | ❌ HTTP 500，直接失败 |

**结论：**

1. **「6G 只能跑 4k」是错的**，实际上 **16k 完全放得下显存，速度一点不掉**。
2. 32k 也行，代价只有 4%（29→28.9 tok/s），因为 32GB 内存接住了溢出的部分。
3. 真正的墙在 **32k 与 64k 之间**。
4. 原因：R1-Distill-Qwen-7B 是 **GQA 架构（4 个 KV head）**，KV cache 约 56KB/token，8k 上下文才 0.45GB —— 比传统 MHA 模型省 7 倍。

> ⚠️ 注意：上表的速率是「短提示 + 生成」测的。**长提示词的 prefill 会慢很多**，那是算力瓶颈（天花板 3），跟显存无关。
>
> 🔧 **2026-10-18 09:35 修正（见 `docs/05-基线测试报告`）**：
> - 实测 **OpenClaw 每轮基础提示就要 10,861 tokens**。所以 **经 OpenClaw 调用本地模型时，num_ctx 最低 16384，8k 会截断**。
> - 更优选择：**`qwen3.5:4b`（4.2B, Q4_K_M）在 32k 仍全显存、57 tok/s**，比 ds7b 快一倍且不掉速 → 直接用它，num_ctx 设 32768。
> - 仅在「直连 Ollama API、不经 OpenClaw」时，8k 才够用。

## 三、预处理：能提升什么，不能提升什么

### 有效的（按 ROI 排序）

| 手段 | 作用 | 为什么有效 |
| --- | --- | --- |
| **1. 检索压缩** | 只喂 top-3~5 个相关片段，每段 ≤500 token | 直接把 10k 的输入压到 2k，同时提高信噪比 |
| **2. 任务分解** | 长任务拆成 3~5 个子任务，每个 ≤2k 上下文 | 规避 7B 的长上下文注意力衰减 |
| **3. 输入规格化** | 自然语言需求 → 结构化 spec / 接口签名 / 伪代码 | 7B 对"明确结构"的执行力远高于"口语描述" |
| **4. 上下文外置** | 状态写 `TODO.md` / `state.json`，每轮只读需要的部分 | 用文件当外部记忆，避免整段重放 |
| **5. 提示去冗余 + 术语表** | 统一术语、删客套 | 减少 prefill 算力，降低歧义 |
| **6. 固定前缀模板** | system prompt 固定在前，few-shot 放前面 | 命中 prefix cache，prefill 几乎免费 |

### 不能提升的

- **不能把 7B 变成云端模型。** 预处理的本质是"降低任务难度"，不是"提高模型能力"。任务本身需要多跳推理时，压缩上下文也救不回来。
- **不能替代工具执行。** 让模型"推理出"文件内容，不如直接读文件。

## 四、后处理：这是 ROI 最高的一环

**核心思想：把「准确率」从模型转移到程序。** 模型只负责生成候选，正确性由代码判定。

| 手段 | 做法 | 收益 |
| --- | --- | --- |
| **程序化校验** | lint / type-check / 单元测试 / JSON Schema / 正则 | 机械性错误（语法、格式、漏字段）拦截率接近 100% |
| **失败自修复循环** | 把报错原文回喂模型，最多重试 2 次 | 7B 修小错的能力其实不差，缺的是"知道错了" |
| **best-of-N + 选择器** | 采样 3 次，用测试/规则选最好的 | 成本 ×3，成功率显著上升 |
| **输出归一化** | 容错解析、补全缺失字段、剥离 `<think>` 标签 | 消除格式抖动 |
| **引用校验**（RAG） | 检查答案里的断言是否真能在检索片段中找到 | 直接打压幻觉 |

> 你现在的模型输出带 `<think>` 标签，这本身就是需要后处理剥离的东西 —— 否则会污染下游解析。

## 五、联网搜索 / RAG：对 7B 的正确用法

方向是对的，但**关键不在"搜"，在"裁"**。

7B 的短板不是"不知道"，而是**长文读不准**（needle-in-haystack 能力弱）。所以：

| 做法 | 说明 |
| --- | --- |
| ✅ 检索后裁剪 | 只要 top-3~5 片段，每段 ≤500 token；宁可少给，不要整页塞 |
| ✅ 强制引用 | 要求输出 `[1][2]` 并在后处理里校验引用编号存在 |
| ✅ 搜索失败要降级 | 超时/无结果时明确告知"未检索到"，**不要让它自由发挥** |
| ✅ 检索用专门的 embedding 模型 | `bge-m3` / `nomic-embed-text`，可跑在 CPU，别用生成模型兼职 |
| ❌ 别把整篇网页塞进 16k | 上下文越长，7B 越容易"看到但用不上" |
| ❌ 别指望搜索结果自动纠错 | 7B 会误读证据，必须靠引用校验兜底 |

## 六、技术层优化清单（2060 本，按 ROI 排序）

| 优先级 | 手段 | 具体做法 | 成本 |
| --- | --- | --- | --- |
| **P0** | 提高 num_ctx | **OpenClaw 场景 ≥16384；用 qwen3.5:4b 时设 32768**（32k 全显存零掉速） | 改一个参数 |
| **P0** | 单模型常驻 | `OLLAMA_MAX_LOADED_MODELS=1`、`OLLAMA_KEEP_ALIVE=-1`，避免反复冷加载（第一次冷启花了 117s） | 改环境变量 |
| **P1** | KV cache 量化 | `OLLAMA_KV_CACHE_TYPE=q8_0`，可让 32k 也全进显存 | 需重启 ollama，需验证 0.40.6 是否支持 |
| **P1** | Flash Attention | `OLLAMA_FLASH_ATTENTION=1` | 同上 |
| **P1** | 模型目录迁外接盘 | `OLLAMA_MODELS=/media/user/.../ollama` | 省系统盘 57G |
| **P2** | 换更强的 instruct 小模型 | Qwen3-8B / 14B Q3 + 部分 offload（32G 内存兜底） | 速度会降，需实测 |
| **P3** | 投机解码 / 多模型并行 | — | ROI 低、复杂度高，**暂不建议** |

> `OLLAMA_KV_CACHE_TYPE` 与 `FLASH_ATTENTION` 需改 systemd 环境后重启 ollama，会影响在跑的网关，**建议停机窗口做**，并先备份配置。

## 七、控制端（本机 Windows）能做什么

本机不跑模型，但**前后处理是 CPU 活**，正好放在这台：

| 分工 | 放在本机的理由 |
| --- | --- |
| 文档抽取 / 切片 / 清洗 | 纯 CPU，Python 即可，不占 2060 显存 |
| Prompt 组装（模板 + 检索片段拼装） | 毫秒级，本地做比走网络快 |
| 后处理校验（lint / 测试 / schema） | 本机已有 Python/Node，无需上 2060 |
| 评测脚本与回归集 | 通过 SSH 驱动 2060，日志落本机，2060 只出推理结果 |
| 日志归集、云端/本地对比报表 | 数据分析放本机，减轻 2060 负担 |
| OpenClaw Web UI | SSH 隧道 `-L 18789` 后在本机浏览器用 |

**边界（重要）：**

- 本机 **C 盘只剩 29GB** → 不要在本机建大索引/向量库；索引放 2060 外接盘。
- 本机 **16GB 内存** → 跑 embedding 要限量；更好的方案是 embedding 也放 2060（CPU 跑，32G 内存够），本机只做编排。
- **推理永远不落本机**（无独显，纯属浪费）。

一句话：**本机 = 编排 + 前后处理 + 评测；2060 = 纯推理 + 存储。**

## 八、系统级适配

1. **三维路由，而不是「简单/复杂」二分**
   按「上下文需求 × 是否需工具调用 × 准确率要求」三轴判断：
   - 短上下文 + 无需工具 + 容错高 → 本地 7B
   - 需多轮工具调用 / 需高准确率 → 云端
   - 长上下文 → 先压缩，压缩后仍长 → 云端
2. **确定性优先（rule-first）**
   能用脚本、模板、正则解决的，不要交给模型。模型只处理"没有确定解法"的部分。这一条对成功率的提升，往往超过所有 prompt 技巧。
3. **状态外置 + 断点续跑**
   长任务每步落盘，失败从断点续，避免整段上下文重放（省 token 又省显存）。
4. **双模型链（分层而非纯 fallback）**
   7B 做摘要 / 规划 / 草稿，云端做关键决策与终审。比"本地失败才切云端"更省。
5. **工具集收敛**
   7B 对工具选择的准确率随工具数量下降。同一 agent 暴露的工具 ≤5 个。
6. **回归集**
   把 `testcases/01~03` 固化成回归集，每次改配置必跑一遍，否则无法判断"优化"是否真的有效。

## 九、建议的执行顺序

```
0. 先建基线        ← 现在一条真实任务都没跑过，没有基线，任何"优化"都无法证伪
1. num_ctx → **16384 起（OpenClaw 场景）/ 32768（qwen3.5:4b）**  ← 零成本，实测掉速为 0
2. 后处理校验层     ← ROI 最高，成功率提升最明显
3. 检索压缩 + 引用校验
4. 三维路由 + 确定性优先
5. KV 量化 / 换更强小模型
6. 投机解码         ← 最后考虑，甚至不做
```

## 十、不建议做的事

1. **没有基线就开始优化** —— 你无法判断改动是变好还是变坏。
2. **指望 prompt 工程让 7B 达到云端水平** —— 能力天花板是硬的，只能逼近不能突破。
3. **在 6GB 上硬塞 14B 全 GPU** —— 必然溢出，速度断崖。
4. **给 7B 配复杂 JSON Schema + 多工具并行** —— 工具调用失败率会飙升；改用单函数 + 文本协议更稳。
5. **在 OpenClaw 场景下把 num_ctx 设成 8k** —— 基础提示就 10.9k，会直接截断（详见 docs/05 修正）。
